# 07 号业务观测与日志采集汇报讲稿

总时长目标约 11 分钟。时间为建议值，应根据实际语速和彩排调整。

## 第 1 页 校园 Wi-Fi 实验的业务观测与证据质量

【建议 40 秒】大家好，我是 07 号，负责业务观测、日志采集和质量检查。我的任务不是替 A、B、C 组预设实验效果，而是明确每个指标的来源、单位、统计窗口和限制，让后续结论可以回到原始记录。接下来先介绍统一口径和采集链路，再讲原始日志中的异常，最后对照三组抽样复现及追加诊断的结果。所有数字都是当前仿真条件下的观察，正式服务阈值仍需团队确认。

## 第 2 页 指标定义与统计窗口

【建议 90 秒】业务目标必须先转成可核查的指标。吞吐量取接收端单位时间接收的有效数据，单位是兆比特每秒。多条流只有在统计窗口对齐且互相独立时才可以解释为总量。RTT 来自探测包的往返时间，除了均值，还可以用 P95 观察尾部。UDP 丢包率要把同流同窗口的丢失包数与总包数一起保留，抖动则沿用 iperf3 接收端定义，单位毫秒。B 组切换附近的连续成功回包间隔包括正常的探测周期，它描述的是采样可见的业务间隔，不能等同协议级切换耗时。本次复核 P95 用最近秩，也就是排序后第 ceil 的百分之九十五位置。08 号的早期草案曾建议线性插值，因此最后采用哪种算法还需要共同确认。阈值、有效分母和缺测处理同样未定，不能把运行状态 PASS 直接解释为业务达标。

## 第 3 页 从原始日志到可复核数据

【建议 80 秒】一次运行首先要记录实验编号、对照策略、终端数、信道、方向、各流负载、运行时间、重复编号和软件版本。随后保存原始输出，包括 AP 和终端的 iw 信息、逐包 ping、iperf3 两端结果，以及 C 组的 tc 队列配置和计数。07 号把原始文件和整理结果分开放置，并通过运行编号、终端和源文件路径建立对应。下载时对服务器下载前后与本地文件做 SHA-256 对比，确认副本完整；这个校验只证明文件内容一致，不自动证明实验设计正确。整理时要检查状态、样本数、端点、窗口以及时钟能否对齐。未适用和没有采到都留空并说明原因，真正测得的零值保留为零。最后给 08 号提供字段字典、指标表、异常记录和原始日志索引。

## 第 4 页 A 组复现：并发接入与信道

【建议 75 秒】A 组选中的是四台终端、两个 AP 使用信道一和六的正式运行。终端向同一服务器并发发送，各终端使用独立端口。原运行四条 TCP 接收汇总之和为 71.922 兆比特每秒，07 号复跑为 71.924。四条定速 UDP 流在这两轮中都报告零丢包。这不代表所有配置都稳定。四条流起始时间都落在同一秒，但分辨率不足以证明窗口完全对齐。TCP 在预热后统计，ping 从分轮开始采集，未按同样方式去除前十秒。我们也补查了 08 号指出的十二终端第二轮：sta7 和 sta8 的前五个探测序号 RTT 较高，抬升全轮平均值，后续响应的描述性均值约二十四毫秒。原日志缺少逐包绝对时间，不能断定原因，也没有从正式统计中剔除这些值。原抽样运行未保存脚本哈希，无法证明脚本逐字一致。

## 第 5 页 B 组：定位并避开信号异常

【建议 100 秒】B 组主要关注移动终端的关联和业务连续性。原 LLF 复跑中，375 个信号样本有 101 个是正数，最高到正 124 dBm。检查原始 iw 输出后发现，正数已经出现在终端和 AP 侧的记录中，并不是整理 CSV 时漏掉了负号。进一步检查服务器使用的 wmediumd 源码，发现对数距离模型直接使用距离的对数，而原路线起点和终点恰好与两个 AP 坐标重合。我们因此在个人目录复制实验脚本，仅将移动路线向旁边偏移两米，避免与 AP 零距离。LLF 和 SSF 各做一次 pilot，两个试跑各 375 个信号样本都没有正值，且都观察到从 AP1 到 AP2 的关联变化。这支持近距离模型边界导致异常的判断，但不足以确定正数具体来自哪个数值转换环节。SSF 试跑仍有三次探测未收到，说明信号数值正常不代表业务无中断。偏移路线改变了实验条件，不能替换旧正式轮，需要 03 和 05 号确认后统一重做正式对照。

## 第 6 页 C 组：交错复测出口拥塞

【建议 110 秒】C 组原 baseline 正式轮 UDP 丢包率为百分之零点三五八，而 07 号复跑为百分之一点九八，出现明显波动。我们没有把它当成必然故障，也没有删除异常点。两轮使用相同父类限速，出口共享队列的累计丢包分别为 82 和 334 个，整轮 CPU 忙碌都在百分之五十多。这支持出口拥塞及队列竞争有关，但队列总丢包覆盖所有业务，不能与 UDP 丢包一一对应，也不足以完全排除调度因素。接着保持两兆比特每秒总限速、三百千比特每秒 UDP 和后台 TCP 不变，交错进行了 baseline 与 QoS 各三轮诊断，每轮六十秒，统计后五十秒。baseline 的 UDP 丢包在百分之零点九一到一点一零之间，QoS 三轮都为零。QoS 的队列总丢包仍有五十、五十五和五十九个，所以只能说当前条件下实时 UDP 丢包得到缓解，不能说所有业务都零丢包。该结果属于服务器仿真出口管理，不代表空口 EDCA，也不能直接推断真实音视频体验。

## 第 7 页 异常核查：状态与证据分开

【建议 95 秒】异常检查要把采集状态、指标表现和证据有效性分开。B 组原始信号异常应保留原值，不能把正数简单改成负数。因为原脚本把操作者固定写成 wifi05，而我们的复跑实际由 wifi07 启动，所以必须在外部复现记录中补充实际操作者，不能改写原始配置。B 的服务器 UDP JSON 里 end.sum 可能显示零字节，而 end.sum_received 仍有非零接收字节；整理时应核对具体字段和接收端来源。C 的 filter JSON 在当前环境中只保留了部分匹配项，因此要用原始 tc 文本确认 UDP 协议、端口和目的地址，再结合类计数看流量是否经过。最后，PASS 只说明运行器完成自身检查，COLLECTED 只说明日志已采集；业务是否达标要另按确认后的阈值判断。

## 第 8 页 交付内容与结论边界

【建议 70 秒】目前已经整理字段字典、运行记录模板、原始日志索引、复算指标和异常检查说明。三组各抽取了一次正式原运行，也分别执行了一次复跑；C 组另外做了六轮交错诊断。原运行、复跑和诊断必须分别归档，不能把额外诊断直接混入原来的正式样本。P95 最终算法、分析窗口、业务阈值以及缺测和失败如何进入分母，仍需要和 08 号及组内确认。B 的偏移路线是一项诊断方案，正式实验如果采用，两个策略应在同一路线上重新采集。整个项目使用仿真和合成流量，因此数据能够帮助解释当前条件下的网络现象，但不能直接代替真实校园环境或应用体验测试。谢谢大家。
