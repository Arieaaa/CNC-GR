# B 信号异常与 C 丢包波动诊断

状态：已完成隔离试跑和六轮 C 诊断；旧 baseline 的波动仍有随机性，不能确定每个丢包的精确位置。诊断试跑单独归档，不覆盖此前正式运行，不能与正式组数据混算。

## B 信号值：零距离模型边界

### 观察

原路线 sta1 从 (15,25,0) 出发并停在 (70,25,0)，恰好与两个 AP 的坐标重合。原正式 LLF 第 3 轮和 07 号复跑各有 375 个有效信号样本，其中各有 101 个正值；07 号复跑范围为 −75 至 +124 dBm。正值集中于起止附近，`iw.jsonl` 原始 `iw dev ... link` 和 AP 侧对应终端的 station dump 均出现正值，说明并非 CSV 的正负号解析问题。

服务器部署的 wmediumd 源文件 `/opt/wifi-lab-src/wmediumd/wmediumd/config.c` 的 `calc_path_loss_log_distance` 根据节点坐标计算 `d`，直接使用 `PL = PL0 + 10 * exponent * log10(d) + Xg`，未在该函数中限定最小距离；原路线存在 `d=0`。这是 log-distance 距离项的边界问题。源码提交见 [wmediumd config.c](https://github.com/ramonfontes/wmediumd/blob/63e9fc995cfb260065c7a0d4c2b14f715f224436/wmediumd/config.c)。此证据支持零距离/极近距离导致信号异常，不能仅凭这些信息断言正值具体是哪个整数转换环节造成，也不能将旧正值简单改成负数。

补充的同一路线 SSF 单次试跑 [expB_pilot_ssf_91_20261111T082617Z_9am2o4k0](../原始日志/expB_pilot_ssf_91_20261111T082617Z_9am2o4k0/) 也有 375 个有效信号样本、0 个正值，范围 −72 至 −38 dBm；观测到 AP1 到 AP2，首次新 AP 位置 x≈43 m。ping 为 375 发、372 收；切换附近最大相邻成功回包间隔约 832.36 ms，有 3 个缺失序号。信号数值异常已通过改变路线在这两轮试跑中避开，业务探测仍有缺包，应另行保留，不能称为无中断。两次试跑均为 `COLLECTED`，不是正式重复对照。

若要把新路线作为正式实验方案，需与 03/05 号确认，并使 SSF/LLF 使用相同偏移路线、重新试跑和重复采集；不要混用原路线结果。真实设备信号仍需实测。

## C 丢包波动

此前 baseline 的原第 2 轮与 07 号复跑分别有 42/11721 与 232/11718 UDP 丢包；运行器汇总的最终共享 bfifo 队列丢包计数分别为 82 与 334，CPU 忙碌约 54.45% 与 53.50%，两轮 steal 均为 0%。这些计数是队列全部业务的总量，不等于 UDP 丢包；相关性支持拥塞与丢包有关，但不单独证明所有丢包都发生在该队列，也不证明 CPU 无任何瞬时影响。

以相同 2 Mbit/s 父类上限、相同 300 kbit/s UDP 和后台 TCP、每轮 60 秒（统计后 50 秒）交错运行 baseline/QoS 各 3 次诊断。6 个独立目录均为 PASS、各 631 个文件，下载时逐文件 SHA-256 与服务器前后核对一致。使用[复算脚本](复算C诊断.py)从接收端逐秒区间和逐包 ping 独立复算，并核查每轮 60 个队列配置快照；详细数值见 [C 交错复测 CSV](C交错复测_20261111.csv)。

| 诊断策略 | 3 轮 UDP 丢包率 | 3 轮队列总丢包数 | 3 轮 RTT P95 |
|---|---|---|---|
| 共享 baseline | 0.9127%、1.0415%、1.1015%；均值 1.0186% | 159、200、200 | 149、135、138 ms |
| 分类 QoS | 0%、0%、0%；均值 0% | 50、55、59 | 0.514、0.386、0.430 ms |

复算确认两组同一父类 2 Mbit/s、QoS 实时/后台类 600/1400 kbit/s，配置在采样快照中保持不变；QoS 的 UDP/ICMP 过滤文本、实时类在 ping 启动前已有字节、以及最终两类字节均被检查。共享 baseline 的 UDP 丢包和队列累计丢包同时增大，结合相同限速和持续 TCP 竞争，证据支持出口拥塞及队列竞争是主要机制；队列计数覆盖所有业务、计数窗口与 UDP 稳态统计窗口不完全相同，不能证明单个 UDP 包的丢失位置，也无法仅凭这些记录排除调度等因素。

原轮组内 baseline 丢包率本就有变化，诊断中共享 baseline 仍波动。启用现成分类 QoS 后，本次三个额外诊断轮的稳态 UDP 丢包均为 0%，表明该条件下实时流丢包得到缓解；QoS 根队列仍有总丢包，不能称作所有业务零丢包或保证未来无波动。结果适用于本仿真出口和当前负载，不代表真实视频体验。两种方案还改变叶队列划分和最低份额，不能把效果单独归因于某一条 filter。任何正式方案变更须与 06 号确认，不覆盖或混入原正式数据。
