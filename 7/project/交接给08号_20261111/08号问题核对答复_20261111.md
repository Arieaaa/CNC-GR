## 2. B 组事件指标与信号异常

“切换附近最大相邻成功回包间隔”的表述合适：它包含正常探测间隔，受探测周期、采样和事件窗口影响，不等同协议层精确切换耗时。全程成功应答 P95 和局部回包间隔是不同统计量；即使全轮最终 375 发/375 收，也可能有较长回包间隔。

保留原日志 `121 dBm` 而不用于解释策略差异是正确的。随后已做隔离诊断：原路线与 AP 坐标重合；服务器 wmediumd 的 log-distance 实现直接使用 `log10(d)`，未在该函数中限制最小距离。将移动站路线的 y 坐标由 25 改为 27 m 后，LLF 和 SSF 各一轮 pilot 均为 0/375 正信号值，且均观察到关联变化；SSF 仍有 3 个探测包未收到。证据支持零或极近距离触发模型边界异常，但无法仅凭现有数据证明正值产生的具体数值转换环节。

偏移路线是**新的诊断配置**，不能替换原有 6 轮正式数据；是否采用并按相同路线重新采集，需 03/05 号确认。详情见 [B/C 诊断记录](../诊断试验/B信号与C丢包诊断_20261111.md)。

## 3. C 组 baseline 波动

与接收端原始日志一致：原轮选入 50 个完整区间，其中 8 个有丢包，共 42/11721；复跑选入 50 个完整区间，其中 32 个有丢包，共 232/11718。按开始时间划为五个连续约 10 秒段，复跑丢包数依次为 **26、42、42、78、44**，所以并非只有一个短暂区间造成差异。区间边界按现有复算允许毫秒级偏移，不能把此结果解释为精确同步抓包。

补充队列证据：原轮和复跑最终共享队列的总丢包数分别为 82 和 334；该计数覆盖所有业务、时间范围也不同于 UDP 后 50 秒统计，不能与 UDP 丢包逐包等同。两轮 CPU 忙碌均约 53%–54%，这不能排除瞬时调度影响。队列计数和相同限速下的持续后台竞争**支持出口拥塞及队列竞争是主要机制**，但不能证明每个 UDP 包的丢失位置或唯一成因。

后来在相同 2 Mbit/s 出口上限、300 kbit/s UDP 和后台 TCP 条件下交错进行 baseline/QoS 各 3 轮诊断。baseline 的 UDP 丢包为 0.9127%、1.0415%、1.1015%，QoS 三轮均为 0%；QoS 的全业务队列仍有 50、55、59 个丢包。它支持当前配置下 QoS 缓解实时 UDP 丢包，不等于所有业务零丢包或以后不会波动；诊断轮不能混入原正式统计。数据和范围见 [C 诊断复算](../诊断试验/C交错复测_20261111.csv)。

## 4. C 组 QoS 队列证据

08 号的表述没有超出已检查证据：正式 QoS 第 2 轮的原始 `configured-srv-filter.txt` 同时包含 UDP 协议、源端口 5202、目的地址和流向实时类的匹配条件；实验 ping 启动前实时类已有字节计数，结合运行器先启动 UDP 的过程，**支持** UDP 进入实时类。它是类级计数，不能说每条 filter 均有独立命中计数。`tc -j` 的 filter JSON 未完整保留各条 u32 match，故检查完整规则应引用文本。

此前抽样复跑的是 **baseline**，额外检查的 QoS 正式轮不是 QoS 复跑。后续新增的 QoS 三轮是单列的诊断复测，也不改写原 24 轮正式统计。

## 统计口径与交付建议

本次 P95 复核沿用各组的最近秩 `ceil(0.95×n)`；是否全组统一采用该算法仍需与 08 号确认。50 ms、1% 仍是示例，阈值、统计窗口、判定单位、缺测及失败轮次分母须由组内确认后再算达标率。`PASS`、`COLLECTED` 和业务达标应分别记录。
